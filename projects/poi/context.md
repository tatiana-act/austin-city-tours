## DOMAIN

[из кода] Сайт-витрина авторских пешеходных экскурсий по Остину и окрестностям
(Джорджтаун, Раунд-Рок, Бремонд-блок, Хайд-парк — `data/tours.ts`), которые водит
один гид — Tatiana Orlova (`app/[locale]/layout.tsx` schema.org Person,
`messages/*.json` → `About`). Next.js 16 App Router, две локали ru/en, статический
контент из TS-файлов репозитория. Пользователь смотрит программы и расписание и
оставляет заявку одной из трёх форм; заявка уходит строкой в Google Sheets плюс
мгновенным сообщением в Telegram гиду.

[решено, владелец] **Приоритет работ на сейчас — органический поиск.** Сайт должен
стать заметнее в Google; соцсети — вспомогательный канал. Практическое следствие:
SEO-решения в коде (ручной hreflang, canonical, sitemap, JSON-LD, Core Web Vitals)
не «инфраструктурная мелочь», а основная поверхность продукта, и любая правка,
которая их задевает, требует явной проверки. См. DEFINITION_OF_DONE и вопросы 16, 17.
[решено, владелец; сейчас отсутствует] Возможное направление на будущее — контент,
связанный с **городскими событиями в Остине** (фестивали, городские даты и т.п.).
В коде сегодня такого нет ни в каком виде: ни сущности, ни данных, ни страниц.
Жёстких сроков и сезонности владелец не назвал. Терминологическая мина на будущее
описана в GLOSSARY, вопрос 24.

[решено, владелец; в работу не брать] Согласованное направление на будущее —
постоянная индексируемая страница на каждую программу экскурсии. Крупное изменение,
сейчас не начинаем; текущие правки не должны делать его дороже (детали в вопросе 16).

Что продукт НЕ делает [из кода]:
- Нет онлайн-оплаты, корзины, платёжного провайдера. Цена — только текст
  (`TourCard`, `UpcomingTourCard`).
- Нет аккаунтов, авторизации, сессий, админ-панели.
- Нет базы данных и CMS. Каталог программ (`data/tours.ts`, `data/tours.en.ts`),
  расписание (`data/upcomingTours.ts`) и прошедшие туры (`data/RecentTours.ts`)
  правятся коммитом в репозиторий.
- Нет подтверждения брони и учёта мест: форма только пишет заявку, дальше диалог
  идёт вне сайта. Ограничение «15 человек» — это верхняя граница `groupSize` в
  zod-схеме (`app/zbkschema.ts`), а не подсчёт остатка мест. Раньше оно же
  дублировалось текстом в поле `included`, но это поле удалено (PR #42).
- Нет email-отправки (никакого SMTP/Resend/Nodemailer в зависимостях).
- Нет API-роутов: всё через Server Actions (`app/actions/*`).

## USERS

[из кода] Язык интерфейса: `en` и `ru`, префикс в URL всегда
(`i18n/routing.ts`, `localePrefix: 'always'`, defaultLocale `en`).
[решено, владелец] **Правило выбора локали:** если посетитель вероятно понимает
русский — отдаём RU; во всех остальных случаях EN как язык по умолчанию. Это
осознанное решение, а не побочный эффект. EN остаётся `defaultLocale` и
`x-default` для поисковиков; RU — целевой опт-ин по языку браузера.
[из кода] Реализация правила: `middleware.ts` подменяет `Accept-Language` на `ru`,
если строка содержит `ru`, `uk` или `kk`, и тем самым даёт RU приоритет над EN.
Реализация **уже́** правила: языки, чьи носители почти наверняка понимают русский,
под условие не попадают — `be` (беларуская), `ky`, `uz`, `tg`, `hy`, `az`, `ka`.
→ вопрос 15.
[из кода] Язык контента ≠ язык интерфейса: `data/tours.ts` — русский текст,
`data/tours.en.ts` — английский, это два независимо поддерживаемых файла, выбор по
`locale === 'en'` (`app/[locale]/page.tsx:27`).
[из кода] Устройство учитывается на сервере: `app/[locale]/page.tsx:26` определяет
мобильный по user-agent (`/android.+mobile|ip(hone|[oa]d)/i`) и передаёт
`isMobileDevice` в `HomeClient` — мобильный список туров сокращён, свёрнутые карточки
тапабельны (коммит b8215b2). То есть мобильный трафик считается основным.
[из кода] Канал распространения — соцсети: кнопки «Share on Facebook» / «Share on
Telegram» на карточках событий (`messages/*.json` → `Upcoming.shareOnFb/shareOnTg`),
ссылки на Instagram `austin.tx.guide` (коммит b4b78cf), ссылки на посты в группе
Facebook через `eventUrl` у прошедших туров. Компонента `FBPost.tsx` больше нет —
эмбед был нерабочей заглушкой и удалён (PR #35).

[решено, владелец] **Два типа посетителя**, оба целевые:
1. **Турист** — приехал в Остин, ищет экскурсию с гидом для себя.
2. **Местный житель** — ищет экскурсию не для себя, а для приехавших к нему
   гостей. Смотрит и выбирает один человек, идёт на экскурсию другой.

Следствия для работы над сайтом (выведено из двух типов, не из кода):
- Тексты и CTA не могут предполагать «ты идёшь сам»: местный бронирует за других,
  ему нужны переносимые артефакты — ссылка на конкретную дату
  (`/tours/[tourEventId]`), кнопки Share в Telegram/Facebook, точка встречи с
  картой. Всё это в коде уже есть и работает именно на этот сценарий.
- Локаль посетителя не обязана совпадать с локалью гостей: местный
  русскоязычный житель может искать англоязычную экскурсию для гостей и наоборот.
  Поэтому переключатель языка (`LanguageSwitcher`) — не декорация, а часть
  основного пути.
- «Турист» и «местный» приходят на разной дистанции до даты: турист — на
  ближайшие дни своей поездки, местный — под заранее известный приезд гостей.

[решено, владелец] **Каналы:** промо в соцсетях даёт небольшие всплески трафика —
это фактическое состояние, но не то, на что делается ставка. Целевой канал —
**поиск**: главная задача продукта сейчас — сделать сайт заметнее в органическом
поиске. Соцсети остаются вспомогательным каналом (в т.ч. пересылка ссылок местными
своим гостям — см. тип посетителя 2), но приоритет работ определяет поиск.

Цифр по числу заявок в неделю и разбивки по формам пока нет — не измеряется.

[решено, владелец] **Сценарии кроме групповой экскурсии по расписанию:**
- **Индивидуальный тур** — обсуждается с гидом лично, вне сайта. Улучшать этот
  путь сейчас не нужно. То есть `BookingForm` с произвольной датой — намеренно
  просто «оставь заявку», а не конструктор тура; отсутствие UI-названия у этого
  сценария не дефект.
- **Корпоративные туры** — важное направление, но контента под них пока нет.
  Значит это не задача «сделать страницу», а сначала «получить текст». В коде
  сегодня нет ни отдельной программы, ни признака корпоративности у события.

## GLOSSARY

Термины, которые НЕ синонимы [из кода]:

- **TourProgram** (`types/tour.ts`) — программа/маршрут, постоянная сущность.
  Строковый id вида `Acap`, `Haust`, `Gcrt`, `Hyde`, `Brmn`, `Milt` (12 штук).
  Живёт в двух файлах-переводах.
- **UpcomingTourEvent** — конкретная дата проведения, id вида `tour74`,
  ссылается на программу через `tourProgramId`. «Тур» в расписании ≠ «тур» в
  каталоге. Роут `/[locale]/tours/[tourEventId]` принимает id **события**, не программы.
- **PastTourEvent** — прошедшее событие, расширяет `UpcomingTourEvent` полями
  `eventUrl`, `eventImage`, `feedbacks`. Хранится отдельно в `data/RecentTours.ts`.
  `lib/tourSchedule.ts` дополнительно перекладывает в «прошедшие» те события из
  `upcomingTours`, время которых уже наступило.
- **Booking ≠ Contact.** Это две разные формы, два разных листа таблицы:
  `BookingForm` (кнопка «Book a tour» в `Hero` и на странице About) → action
  `submitBookingForm` → лист `Bookings`. Кнопки «Reserve» на карточке программы и
  «Join this tour» на карточке события открывают `ContactForm` через
  `BookingManager` → action `submitContactForm` → лист `Contacts`. Слово
  «бронирование» в UI покрывает оба пути, в коде это разные вещи.
- **Review / Feedback** — одна сущность, лист `Reviews`, но два направления:
  `FeedbackForm` пишет строку `[name, tour, tourId, date, '', text]`, а
  `readAllFeedbacks.ts` читает и **показывает отзыв только если колонка E непустая**
  (`convertToReviews`: `text: (row[4] ?? '').length > 0 ? (row[5] ?? '') : ''`).
  То есть колонка E — ручной модерационный флаг: свежий отзыв попадает в таблицу
  скрытым, пока гид не заполнит E в Google Sheets. Кэш чтения — 1 час
  (`unstable_cache`, ключ `reviews-v2`).
- **price у программы ≠ price у события — и это осознанное решение.**
  [значение — от владельца] Цена задаётся у события, потому что тур с бонусом
  может стоить дороже: цена принадлежит дате, а не маршруту. Программа —
  многоразовая сущность, её цена не может учесть, что 30 августа добавили этап Д.
  [из кода] У 9 из 12 программ `price: 0`, у событий обычно `price: 40`. Итоговая
  цена = `event.price ?? program.price`.
  **Ловушка, следующая из этого:** `price` у события опциональный
  (`price?: number`), а у большинства программ он `0`. Забыть цену у новой даты =
  страница тура объявит его бесплатным: `app/[locale]/tours/[tourEventId]/page.tsx`
  печатает `price > 0 ? цена : t('free')`, то есть «Бесплатно». При этом карточка в
  списке (`UpcomingTourCard`) при отсутствии цены не покажет ничего —
  `price !== undefined`. Два вида одного события скажут разное. Цена у программы в
  карточках вообще не выводится: строка закомментирована в `TourCard.tsx:88`, то
  есть `price: 0` у программ — мёртвая заглушка, которая оживает только как этот
  fallback. → вопрос 27.
- **Central Time.** Все `date`/`time` событий — локальное время Остина; «прошёл /
  не прошёл» считается через `parseCentralTime` (`lib/utils.ts`, зона
  `America/Chicago`), не по UTC и не по часовому поясу браузера.
- **Календарь** — две разные вещи: секция-анкор `#upcomingCalendar` на главной
  (`lib/MyConstants.ts`) и отдельная индексируемая страница
  `/[locale]/tours/calendar` со своим canonical.
- **bonus** [значение — от владельца]: тур в конкретную дату приурочен к городскому
  событию (концерт, парад, салют) или включает дополнительное событие сверх
  заявленной программы, которое участники посетят. Это свойство **события-даты**, а
  не программы, — и потому поле живёт в `UpcomingTourEvent`, а не в `TourProgram`.
  Технически [из кода]: не текст, а ключ перевода, резолвится через
  `tUpcoming(event.bonus)`; произвольную строку положить нельзя.
  **Уточнение владельца, снимающее мою ошибку:** бонус — не обязательно отдельное
  мероприятие. Это может быть **дополнительный этап тура**: обычный тур XX =
  посещение А, Б, В; «XX: бонус Д» = А, Б, В и Д. Городское событие (концерт, парад,
  салют) — частный случай, а не определение. Поэтому существующие ключи
  (`bonusMuseum`, `bonusCap`, `bonusHenryMuseum`, `bonusChat`, `bonusMillet`)
  определению соответствуют — это и есть добавленные этапы. Я ошибочно записал это

    расписание проходит через вас?

Ниже — исходные формулировки; они нужны, если кто-то возьмётся дописывать README.

**C1. README называет Google Sheets базой данных — фактически это не так.**
README: «The specific ID of the Google Spreadsheet to use as your database».
В действительности каталог экскурсий, расписание и прошедшие туры лежат в TS-файлах
репозитория (`data/tours.ts`, `data/upcomingTours.ts`, `data/RecentTours.ts`), и
таблица о них ничего не знает. В Sheets живут только заявки и отзывы.

**C2. README описывает Sheets как «store» (только запись) — код ещё и читает.**
`app/actions/readAllFeedbacks.ts` читает `Reviews!A:F` и рендерит отзывы на главной
и на странице тура, с кэшем на час. То есть таблица — источник контента для
публичной страницы, а не только приёмник заявок. README про это молчит, как и про
модерационный флаг в колонке E.

**C3. Раздел деплоя на Vercel не упоминает Telegram-переменные.**
Шаг 3 списка требует добавить только `GOOGLE_SHEETS_CLIENT_EMAIL`,
`GOOGLE_SHEETS_PRIVATE_KEY`, `GOOGLE_SHEETS_SPREADSHEET_ID` — «identically to your
`.env.local` file». Но выше в том же README перечислены ещё
`TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_CHATID`, и без них
`app/tgmessage.ts` тихо возвращает ошибку — уведомления о заявках не приходят,
при этом форма отвечает пользователю «успешно». README противоречит сам себе.

**C4. README не документирует структуру колонок в листах.**
Сказано только «Spreadsheet should have 3 sheets named `Contacts` `Reviews` and
`Bookings`». Код же жёстко привязан к порядку колонок: `Bookings!A:H` =
`[tourId, date, name, contact, groupSize, created, tour, extra]`, `Contacts!A:F` =
`[name, email, phone, telegram, whatsapp, tour]`, `Reviews!A:F` =
`[name, tour, tourId, date, <флаг публикации>, text]`. Таблица, созданная строго
по README, будет считана неправильно.

**C5. Скрипты в README и в package.json расходятся.**
README упоминает только `npm run dev`. В `package.json` есть ещё `devt`
(`next dev --turbopack`), `test`, `test:watch`, `format`, `lint` — про них не сказано
ничего. Плюс `npm test` создаёт ложное впечатление наличия тестов: единственный тест
закомментирован.

**C6. Имя проекта.** README — «Austin City Tours», `package.json` — `"name":
"city-tours"`, `"version": "4.1.3"`. Версия 4.1.3 в README не отражена и, судя по
истории коммитов, руками не поддерживается как релизная.

**C7. README описывает продукт как «for booking and discovering city tours» —
бронирования в продуктовом смысле нет.** Ни оплаты, ни подтверждения, ни учёта
мест: формы записывают заявку, дальше всё вне сайта. Формулировка README завышает
функциональность.

**C8. В README ничего нет про то, что определяет поведение проекта.**
Не упомянуты: локализация и принудительный редирект `ru|uk|kk → ru`
(`middleware.ts`), `trailingSlash: true`, отключённая оптимизация картинок
(`images.unoptimized`), зашитый домен, FullCalendar, схема JSON-LD и ручной
hreflang, правило «две локали правятся парой файлов». Формально это не
противоречие, а пробел — но человек, читающий только README, сломает всё это
первым же коммитом.

**C9. README: «Vercel will automatically redeploy whenever you push to your main
branch» vs CLAUDE.md: «Do not push to `main` directly, even after a rebase».**
Инструкции описывают несовместимые процессы; фактический процесс — PR в `main`,
автодеплой после мержа.

**C10. Языковая нестыковка внутри самих данных (не README, но того же рода).**
В русском `data/tours.ts` массив `included` заполнен английским текстом
(«Professional tour guide», «Historical maps and materials», «Small group
experience (max 15 people)»), тогда как остальные поля русские. Заметно это станет,
если `included` начнут выводить (сейчас поле не рендерится — см. вопрос 8).
