## 2. Модель данных

Четыре файла. Связь — единственный источник истины о том, какие POI существуют.

### 2.1 `data/poi.programs.ts` — связь программа↔POI

```ts
export type ProgramId =
  | 'Acap' | 'Haust' | 'Gcrt'  | 'Rrock' | 'Brmn'   | 'Auswe'
  | 'Auhnry' | 'Hyde' | 'Acstm' | 'Albjwc' | 'Amhry' | 'Milt';

export const programPoi = {
  Acap: [
    { poi: 'capitol' },
    { poi: 'oldBakery' },
    // …порядок массива = порядок показа
  ],
  Auswe: [
    { poi: 'capitol', day: 1 },
    // …
    { poi: 'georgetown', day: 2 },
  ],
} as const satisfies Partial<Record<ProgramId, readonly PoiRef[]>>;

type PoiRef = { poi: string; day?: number };

export type PoiId = (typeof programPoi)[keyof typeof programPoi][number]['poi'];
```

- Порядок массива — порядок показа **внутри программы** (AC 7). Порядок каталога из
  него больше не выводится: он алфавитный и считается в `lib/poi.ts` (§3).
- `ProgramId` экспортируется: из него типизирована пара `programs[].id` в записи
  каталога, из которой строится адрес перехода (§4.1).
- `day` необязательное. Заполнено только у `Auswe`; у остальных программ отсутствует,
  и список рендерится плоским.
- `Partial<Record<ProgramId, …>>` — программа без POI просто отсутствует как ключ
  (AC 7a).
- Файл **не локализован**: порядок и состав физически не могут разойтись между RU и EN
  (AC 7, AC 16).

### 2.2 `data/poi.links.ts` — атрибуты POI, не зависящие от языка

```ts
import type { PoiId } from './poi.programs';

export const poiMapUrl: Record<PoiId, string> = { … };
```

Фото (R9) добавляется сюда вторым `Record<PoiId, string>` — существующие записи не
переписываются.

### 2.3 `data/poi.ru.ts` и `data/poi.en.ts` — тексты

```ts
import type { PoiText } from '@/types/poi';

export const poiRu: Record<PoiId, PoiText> = { … };
```

```ts
export interface PoiText {

}
```

### 2.5 Инварианты держит компилятор, не рантайм

`PoiId` выводится из таблицы связей, поэтому `Record<PoiId, …>` в трёх остальных
файлах требует **ровно тот же** набор ключей:

| Ошибка в данных | Что происходит | Требование |
|---|---|---|
| POI есть в программе, текста в одной локали нет | отсутствующий ключ `Record` → ошибка `tsc` | PRD AC 3, AC 22 |
| POI есть в текстах, но ни в одной программе | лишний ключ `Record` → ошибка `tsc` | PRD AC 6, AC 22 |
| POI есть, ссылки на карту нет | отсутствующий ключ → ошибка `tsc` | PRD §5, AC 3 |
| Опечатка в id программы | лишний ключ под `satisfies` → ошибка `tsc` | — |
| **Таблица связей пуста** | `PoiId` вырождается в `never`, `Record<never, …>` сходится с пустыми файлами текстов, билд зелёный | §2.6 |

`typescript.ignoreBuildErrors: false` — любая из них роняет `npm run build` и проверку
Vercel. Рантайм-проверок и валидаторов не добавляется. [A §1]

**Чего инварианты не ловят:** опечатку в `poi:` внутри связи. Она создаёт новый id, и
ошибка приходит как «нет текста для `driskil`» — билд всё равно падает, но текст
ошибки указывает не на ту строку.

### 2.6 Третий инвариант: таблица связей непуста

«Таблица связей никогда не пуста» (PRD §5.1, второй пункт «Two states therefore do not
exist») — это условие, а не механизм: пустую таблицу компилятор пропускает, строка
выше. Держать ли его билдом, PRD §10 оставил мне.

**Удерживаю билдом**, тем же способом, что и два остальных инварианта, — утверждением
на типах в самом `data/poi.programs.ts`, без рантайма и без новой ступени сборки:

```ts
type NonEmptyCatalogue = [PoiId] extends [never] ? never : true;
export const catalogueIsNotEmpty: NonEmptyCatalogue = true;
```

Пустая `programPoi` → `PoiId` = `never` → тип константы `never` → присваивание `true`
не проходит → `tsc` падает вместе с `npm run build`. Обёртка в кортеж обязательна:
голое `PoiId extends never` распределяется по union и на `never` даёт `never` по другой
причине, то есть работало бы случайно. Константа экспортируется, чтобы не считаться
неиспользуемой.

Цена — две строки, смысл которых не читается без комментария; выигрыш — состояние,
которое иначе доезжает до прода молча: билд зелёный, ссылка в футере на каждой
странице, запись в `sitemap.ts`, а страница отдаёт заголовок и пустой список. Сегодня
до этого состояния одна строка: в таблице ровно один POI. [A §7]

Что осталось: `mapUrl` в этой форме
по-прежнему нет, то есть решение D2 «карта только на странице списка» держится типом, а
не дисциплиной; а «список печатает имена» (AC 15) теперь держится не формой данных, а
разметочным инвариантом §4.3 и проверкой A9 на отрендеренном HTML.

```ts
/** Запись в виде программы: аккордеон на главной и страница даты. */
export interface ProgramPoi {
  id: PoiId;
  name: string;
  /** Тело всплывающего блока (AC 28). Тот же текст, что печатает страница
   *  списка, — одна запись, читаемая из двух мест (PRD §5). */
  description: string;
  day?: number;
}

/** Запись каталога: страница списка. */
export interface PoiCatalogEntry {
  id: PoiId;
  name: string;
  description: string;
  mapUrl: string;
  programs: { id: ProgramId; title: string }[];
}

export function getProgramPoi(programId: string, locale: string): ProgramPoi[];
export function getPoiCatalog(locale: string): PoiCatalogEntry[];
```

- `getProgramPoi` — в порядке массива связи, с `day` как есть; с v2.4 отдаёт и
  `description` (AC 28). `mapUrl` в этой форме нет и не появляется. [A §10], [A §10.1]
- `getPoiCatalog` — каждый POI один раз (PRD AC 5); `programs` — программы, ссылающиеся
  на него, с **полным** локализованным `TourProgram.title` из `data/tours*.ts`, не
  `shortTitle` (PRD §7.1, AC 8 — поле названо там явно). `id` в этой паре несущий: из
  него строится адрес перехода (§4.1).
- В каком порядке функция **отдаёт** `programs` — порядок обхода таблицы связей; она не
  локализована, поэтому в RU и EN перечень идёт одинаково, различаются только сами
  названия. Как этот перечень показан — design §2.2.
- `programs` не бывает пустым: POI существует потому, что на него ссылается программа
  (§2.5), а `ProgramId` целиком лежит в `data/tours*.ts`, то есть название всегда
  находится. Ветка «программ нет» на странице списка охраняет невозможное.
- `description` не опционально и на пустую строку не проверяется: состояния «место без
  описания» не бывает (PRD §5.1, AC 3) — держится очередью релиза и проверкой §7, не
  типом.
- **Порядок каталога — алфавитный по показываемому имени** (PRD §7.1, AC 26), то есть по
  `name` из локали, которую отдаёт `getPoiCatalog`. Сравнение —
  `new Intl.Collator(locale).compare`, один коллатор на вызов; равенство разрешается
  стабильностью `Array.prototype.sort`, то есть порядком таблицы. [A §2], [A §8]
- Что алфавит стоит — [A §2]; одно следствие видно посетителю и вынесено владельцу
  (§10 п. 9): в RU часть имён латиницей, а латиница в русской коллации идёт перед
  кириллицей.
- Выбор локали — `locale === 'en' ? … : …`, как в `app/[locale]/page.tsx:27`.

Страница списка не монтирует `LanguageSwitcher` и шапки не получает (PRD §7.1, «No page

пропов и новых точек монтирования это не создаёт — вид остаётся тем, что уже собран.

В `TourCard` список мест встаёт **целиком**, между описанием программы и кнопкой
`book-button` (PRD §7.2): усечения, «первых N» и ссылки «остальное на странице мест» в
контракте нет, поэтому `getProgramPoi` не получает ни лимита, ни признака усечения.
`PoiList` стоит рядом с блоком `highlights` и с ним не сводится (PRD R13) — это два
разных списка в одной карточке. **Чем они различаются для читателя — design §3.1**
(там это решено формой, а не подписью), **какой гарнитурой набран перечень — тоже
дизайн** (PRD AC 27, улучшение 1: как блок выше, а не как точка встречи). Мой контракт
лишь в том, что блоков два и данные у них разные.

**Прокидывание в `TourCard`.** `TourCard` и `ToursSection` — клиентские; данные не
импортируются в них, а считаются на сервере и передаются пропом
(`.claude/skills/nextjs-ssr.md`):

```
app/[locale]/page.tsx  →  HomeClient  →  ToursSection  →  TourCard
   poiByProgram: Record<string, ProgramPoi[]>          poi: ProgramPoi[]
```

`app/[locale]/page.tsx` строит `poiByProgram` рядом с существующим `allTours`
(строки 27–32). Три сигнатуры расширяются одним пропом каждая. У `TourCard` пропа два:
второй — признак прибытия (§4.1), и он приходит не из данных, а из состояния
`ToursSection`.

**Свёрнутая мобильная ветка `TourCard` (строки 42–70): ограничение ослаблено, и это
названо, а не сделано молча.** До O20 оно звучало «не меняется, тизер остаётся
тизером». Теперь оно звучит так: **разметка тизера не меняется, меняется условие, при
котором он выбирается**. Прибывшая по ссылке из каталога карточка на компактной
раскладке рендерит развёрнутую ветку, минуя тизер; все остальные карточки на том же
экране остаются тизерами, и при обычном заходе на главную — без якоря
`<id>tour-card` — тизером остаётся и она (PRD AC 25, абзац об ограничении). То есть
изменение точечное и адресное, но утверждать «свёрнутая ветка не затронута» больше
нельзя: затронут её выбор. Приёмка — A4 с той же оговоркой.

### 4.1 Переход «запись каталога → описание программы на главной»

Требование — PRD AC 25, и с ответом владельца от 2026-08-18 (O20) в нём **три
наблюдаемые вещи**: прокрутка к карточке, разворот списка, если карточки не было среди
отрисованных, и **сама карточка приезжает раскрытой — на любой ширине экрана**.
Наблюдаемый результат — PRD, механика — здесь. Реализация внутри контракта — кодера.

Что уже есть в коде и не переделывается: якорь `id={tour.id + 'tour-card'}` в обеих
ветках `TourCard` (строки 44 и 73); разворот всего списка по оконному событию
`show-all-tours-and-scroll` с `detail.tourId` (`ToursSection.tsx:59-79`);
`HashScrollHandler`, смонтированный на главной (`app/[locale]/page.tsx:45`), который
после монтирования опрашивает DOM до 4 секунд и доскраливает по `ResizeObserver`.
Чего нет: межстраничного пути «пришёл по адресу с якорем → развернуть все →
прокрутить», и **никакого пути к раскрытию**: `isExpanded` — локальное `useState`
внутри `TourCard` (строка 17), снаружи им не управляет ничто.

**Звено живёт в `HashScrollHandler`, и шов остаётся один — то же оконное событие.**
`HashScrollHandler` и `HomeClient` — сиблинги под серверным компонентом
(`app/[locale]/page.tsx:45,47`), общего клиентского состояния у них нет, так что
любой другой шов — это новый провайдер или новое событие. Событие переиспользуется, и
за это заплачено: **его смысл шире имени**. Разбор и отвергнутые варианты — [A §9] для
самого звена, [A §9.1] для того, чем доносится «раскрыть».

Контракт:

| | |
|---|---|
| Адрес ссылки | `/{locale}/#{programId}tour-card` — существующий адрес главной с существующим якорем. Нового URL нет, `app/sitemap.ts` не трогается (AC 20, context.md CONSTRAINTS) |
| Кто строит адрес | страница списка, из `programs[].id` (§3) |
| Условие срабатывания звена | хеш вида `<id>tour-card`, то есть оканчивается на `tour-card` и не равен ему. Адреса вида `tour-card-<eventId>` (`RecentEventCard`, `UpcomingTourCard`) под условие не попадают — суффикс другой; `#upcomingCalendar` и прочие якоря не затрагиваются |
| Что делает звено | один раз при монтировании шлёт `show-all-tours-and-scroll` с `detail = { tourId: <id>, expand: true }` — **всегда, а не только когда элемента нет в DOM**: карточка среди отрисованных всё равно должна раскрыться. Дальше продолжает свой опрос и доскроллинг как сегодня |
| Что делает `ToursSection` | по событию: (а) растит список, если нужной программы нет среди видимых, — как сегодня; (б) при `expand` запоминает id прибывшей программы и передаёт вниз признак прибытия ровно одной карточке |
| Что делает `TourCard` | принимает признак прибытия и показывает детали, если: раскладка не компактная **или** посетитель раскрыл карточку сам **или** пришли по ссылке и посетитель её после этого не сворачивал |
| Чего звено не делает | не знает про число карточек, про раскладку и про `tours`; не заводит второго механизма прокрутки — доскраливают уже существующие два пути, оба к тому же элементу |
| Что не меняется | `UpcomingTourCard` — как есть: он шлёт событие без `expand`, и для него поведение прежнее (растим список и прокручиваем, раскрытия нет). Ветка «показать все» в `ToursSection` — как есть по существу |

Два запрета — часть контракта, потому что оба уже стоили проекту работы:

- **Раскрытие не делается `setState` в эффекте.** Правило `react-hooks/set-state-in-effect`
  уже стоило проекту отдельного PR #41 — на соседнем компоненте той же секции,
  `ToursSection` (context.md вопрос 20): каскадные ререндеры, а при ставке на поиск ещё
  и Core Web Vitals. Признак прибытия должен участвовать в вычислении «показывать
  детали», а не переписывать состояние после рендера.
- **Раскрытие не делается перемонтированием карточки** (сменой `key`): узел с якорем
  пересоздаётся, а `HashScrollHandler` держит ссылку на прежний элемент и продолжит
  скроллить к отсоединённому узлу.

Отсюда следует, что состояние карточки перестаёт быть булевым: значимы три случая —
посетитель раскрыл, посетитель свернул, посетитель не трогал. В третьем решает признак
прибытия. Форма записи этого — кодера, важно лишь, что кнопка «свернуть» на прибывшей
карточке обязана работать.

Деградация без JS: ссылка приводит на главную, в секцию программ. Ни разворота, ни
прокрутки, ни раскрытия не будет, тупика тоже нет.

**Что контракт не гарантирует и проверяется руками** (§8 A5): переход из `/places/`
на главную — клиентская навигация `next/link`, и эффект `HashScrollHandler` при
монтировании страницы должен увидеть уже обновлённый `window.location.hash`.
Утверждать это из чтения кода нельзя — проверяется на preview.

**На десктопе раскрывать нечего:** `isCompact` приходит из `useMediaQuery(max-width:
768px)` (`ToursSection.tsx:47`), и при `isCompact === false` карточка развёрнута всегда
(`TourCard.tsx:37`). Требование «на любой ширине» шире, чем работа: механизм нужен
только компактной ветке, а на десктопе выполняется уже существующим кодом.

### 4.2 Прибытие на запись каталога — зеркало §4.1

Требование — PRD AC 29: у каждой записи списка стабильный якорь, ссылка-иконка из
всплывающего блока приводит посетителя **к записи того же места**. Нового URL нет:
адрес существующий, добавляется фрагмент (AC 20, context.md CONSTRAINTS).

| | |
|---|---|
| Форма якоря | `poi-<PoiId>` — например `poi-capitol`. Из идентификатора, а не из имени: имя локализовано, а якорь обязан быть одинаковым в RU и EN, иначе ссылка из RU-аккордеона не найдёт цель на EN-странице |
| Кто его ставит | страница списка, на элемент, которым начинается запись. Какой это элемент — design §2.2; я требую только, чтобы якорь был у записи, а не у имени внутри неё, иначе прокрутка встанет на середине |
| Почему не пересекается с §4.1 | правило §4.1 ловит хеш, **оканчивающийся** на `tour-card`; `poi-capitol` под него не подходит, а `poi-` в качестве префикса не занят ничем `[from code]` |
| Адрес ссылки-иконки | `/{locale}/places/#poi-<id>` — со слэшем перед фрагментом, `trailingSlash: true` |
| Чем прокручивает | **ничем новым: браузером.** `HashScrollHandler` на `/places/` не смонтирован — он стоит только в `app/[locale]/page.tsx:45` `[from code, проверено]`, — и монтировать его туда не нужно |

**Почему браузера достаточно, и при каком условии перестанет.** `HashScrollHandler`
существует ради страниц, которые доверстываются после гидратации: комментарий в нём
называет FullCalendar, а §4.1 — карточки, которых нет в DOM в момент перехода. На
`/places/` ни того ни другого: страница — Server Component, клиентских островов на ней
сегодня нет, весь список приходит в HTML, высота записей не меняется после загрузки.
Значит цель существует в момент прибытия, и родной переход по фрагменту попадает точно.

Условие, при котором это перестаёт быть верным, названо, чтобы отказ не выглядел
неожиданным: как только на странице появится что-то, меняющее высоту после первой
отрисовки — фото (R9) или всплывающий блок, если он когда-нибудь появится и здесь, —
прокрутка начнёт промахиваться, и тогда `HashScrollHandler` монтируется и на `/places/`.
Сегодня это лишний клиентский остров на странице, у которой их ноль. [A §12]

Проверяется A8 — в том числе **на переходе с главной**, где навигация клиентская, а не
загрузка документа.

### 4.3 Всплывающий блок: состояние и разметка

Требование — PRD AC 28: клик по имени в аккордеоне или на странице даты открывает блок с
описанием этого места и ссылкой-иконкой; **открыт не больше одного**; карты в блоке нет.
Облик блока — дизайн. Мои здесь три вещи: что лежит в разметке, где живёт состояние и
что из этого попадает на сервер.

**Разметочный инвариант — то, чем достигается серверная разметка описаний.**

> Узел блока с текстом описания присутствует в выводе рендера **всегда**, для каждого
> места в списке; состояние управляет только его видимостью, а не его наличием.

Отсюда следует ровно то, что решил владелец: текст описаний попадает в серверный HTML
той страницы, где список отрисован, — потому что он часть первого рендера, а не
результат клика. Никакого запроса на клик, никакой сборки узла на клиенте; без JS текст
физически в документе. Это и есть ответ на «чем достигается»: **не механизмом, а
запретом на механизм** — запрещено собирать содержимое блока по требованию.

Обратная сторона того же инварианта — то, что теперь держит AC 15: сам список печатает
имена, а описания лежат в скрытых узлах при каждой записи. Отличить одно от другого в
отрендеренном HTML можно (A9), а вот «список печатает имена» стало утверждением про
видимость, а не про содержимое документа.

**Где живёт состояние.** Список рендерится одним компонентом `PoiList` в двух разных
родителях: клиентский `TourCard` и **серверная** страница даты
(`app/[locale]/tours/[tourEventId]/page.tsx:13` импортирует его напрямую) `[from code]`.
Общего клиентского родителя у них нет — и это перестало быть задачей: состояние никуда
за пределы компонента не выходит.

**Область действия правила задана владельцем** 2026-08-26, дословно: «локального
состяония достаточно». То есть «не больше одного» — **в пределах одного списка**, не
страницы. Мой здесь только механизм.

| | |
|---|---|
| Где | Локальное состояние экземпляра `PoiList`: один `useState` на список |
| Что хранит | id открытого места либо «ничего». Открытие затирает предыдущее — правило «не больше одного в этом списке» выполняется **по построению**, а не проверкой |
| Область действия | список. Соседние списки друг о друге не знают и друг друга не закрывают |
| Чего не нужно | модульного источника, `useSyncExternalStore`, контекста, оконного события, идентификатора экземпляра. Всё это обслуживало общую область действия и отпало вместе с ней. [A §11] |
| Что это делает с `PoiList` | он становится клиентским (`'use client'`) и на странице даты превращается в клиентский остров. Данные `ProgramPoi[]` сериализуемы, серверный рендер разметки сохраняется — то есть инвариант выше не страдает |

**Следствие решения, названное прямо:** на одной странице может быть открыто
**несколько блоков одновременно — по одному на список**. На главной списков на экране
два и больше (каждая развёрнутая карточка программы), на странице даты список один,
поэтому там разницы нет вовсе. Место, попавшее в два списка (`capitol` в `Acap` и
`Auswe`), ведёт себя в каждом независимо: открытие в одной карточке не закрывает блок в
другой. Это принято владельцем, а не упущено; проверяется A10.

Граничный случай, которого данные не создают: если одно место когда-нибудь окажется
дважды **внутри одного** списка (например днём 1 и днём 2 многодневной программы), оба
его блока откроются вместе — состояние хранит место, а не позицию. Сегодня таких пар в
таблице связей нет.

**Разметочный инвариант ответом владельца не задет и остаётся в силе.** Он про наличие
узла, а решение — про область действия состояния; это разные утверждения. Узел блока с
текстом по-прежнему присутствует в выводе рендера всегда, для каждого места, а
состояние — теперь локальное — по-прежнему управляет только видимостью. Серверная
разметка описаний (§4.3.1) от смены области не изменилась ни на строку.

**Чего я не задаю:** как блок выглядит и где стоит, есть ли у него заголовок и крестик,
закрывается ли он по Escape, по клику мимо или повторным кликом. Это дизайн (PRD §10), и
любой их выбор ложится на это состояние без правки контракта.

**Запасная реализация на `<details>` отпала — дизайном v1.3, а не мной.** Она держалась на
том, что блок может оказаться раскрытием в потоке под именем места; дизайн поставил панель
под перечнем **своей группы** (design §3.3), а имени велел течь строчным текстом (design
§3.1), чего `<summary>` не даёт. Строка сохранена, чтобы отмена читалась, а не исчезла.

#### 4.3.1 Ответ, который PRD §10 требует вернуть

**Да, текст описаний попадает в серверную разметку главной.** Механизм — инвариант выше;
никакого другого способа выполнить решение владельца («описание статическое, так будет
быстрее») не существует: всё, что собирается по клику, по определению отсутствует в
серверном HTML.

Что из этого следует для чужого документа, в готовом для переноса виде:

- **R13 читается по большему случаю, а не по меньшему.** Между `/` и `/places/`
  дублируется абзац на место, а не имя. Severity в PRD написана для меньшего случая и
  относится теперь к состоянию, которого не будет.
- **Довод §2.1 про дублирование** должен исходить из того, что тот же текст стоит на
  двух индексируемых страницах, причём главная сильнее.
- **R18 в PRD упомянут в §7.5, но в таблице рисков его нет** `[from code, PRD v2.4]` —
  ссылка висит. Это чужой документ, поэтому только называю.

**Объём дублирования ограничен, и граница считается точно.** В серверный HTML главной
попадают описания только тех программ, чьи карточки отрисованы на сервере, — а там
`useMediaQuery` отдаёт `false`, поэтому `layoutCount = 3` и карточек три
(`ToursSection.tsx:46-51`) `[from code]`. То есть сегодня это места **первых трёх**
программ (`Acap`, `Haust`, `Gcrt`), а не всех двенадцати; остальные приезжают только
после гидратации и в исходном HTML их нет. Число вырастет, когда починят issue #53 —
десктопная раскладка отдаёт шесть.

**Единственное сокращение, доступное без нарушения решения владельца** — внутристраничное:
место, посещаемое несколькими программами, сегодня повторяет свой абзац столько раз,
сколько его списков отрисовано на одном экране (`capitol` в `Acap` и `Auswe` — дважды).
Убрать это можно, вынеся тела блоков из записей списка в одну коллекцию на страницу и
связав их с именами по id. **Не делаю сам, и причин теперь две:** это меняет то, где
узел блока стоит в разметке, а положение блока — предмет дизайна (PRD §10); и общая
коллекция на страницу противоречит локальной области действия состояния (§4.3) — узел
стал бы общим для списков, которые по решению владельца друг о друге не знают. Между
`/` и `/places/` дублирование не сокращается ничем: там это прямое следствие решения
владельца.

#### 4.3.2 Признак контрола и состояние без JS — ответ в тред `D18`

Возражение дизайна: признак «имя кликабельно» — статический CSS, он приезжает с сервера, а
без JS панель не раскрывается, то есть признак обещает раскрытие, которого не будет. Выбор
поставлен из двух — (а) признак ставится только после гидратации, (б) состояние правки не
стоит, — и (а) назван расходом на исполнение. **Расход мой, и он почти нулевой, но только
при одном способе исполнения.** Ниже способ, его цена и запреты, которыми она удерживается.

**Дизайн выбрал (а)** (v1.4 §3.2, тред `D18`): признак условен — без скриптов пунктира и
курсора-указателя нет. Раздел с этого момента описывает не цену выбора, а действующий
механизм; условности в нём больше нет, и её нет ни в S6′ (§7), ни в A13 (§8).

**Способ: признак остаётся в базовых правилах и снимается под `@media (scripting: none)`.**

| | |
|---|---|
| Что двигается | только объявления признака: пунктирное подчёркивание и `cursor: pointer` |
| Что не двигается | разметка. Роль, `tabindex`, `aria-expanded`, `aria-controls`, узлы и текст в серверном HTML те же, что на клиенте, побайтово |
| Клиентское состояние | не заводится: ни флага «смонтировано», ни второго рендера, ни эффекта |
| Инвариант §4.3 | не задет: он про **наличие** узла панели, здесь меняется видимость чужого признака |
| Цена | одно правило в `app/globals.css` |

**Направление правила несущее: признак снимается, а не добавляется.** Браузер, которому
медиа-признак `scripting` неизвестен, запрос не сопоставляет и правило не применяет. Написанный
добавлением (`@media (scripting: enabled)`) признак в таком браузере исчез бы навсегда — редкое
состояние было бы исправлено ценой обычного, и у всех его посетителей. Написанный снятием, он
даёт там сегодняшнее поведение, то самое, которое уже принято.

**Чего этот способ не покрывает, и почему покрыть нечем.** Признак у имени не один: кроме
пунктира и курсора его несут роль кнопки, `tabindex` и `aria-expanded` — без JS элемент
по-прежнему объявляется кнопкой и получает фокус, а нажатие ничего не делает. CSS этого не
снимает, а разметкой снимать **запрещено**: любое расхождение атрибутов между серверным и
клиентским рендером — это несовпадение при гидратации, а в React 19 оно роняет корень в
клиентский рендер целиком `[from code, react 19.2.7]`. Лечимый отказ был бы заменён худшим.

Этим развилка дизайна и распалась: (а) исполняется для **видимой** половины признака
практически даром, а остаток — «без JS имя остаётся кнопкой для скринридера» — меньше
исходного. Дизайн v1.4 §3.5 записал его явно и принял, §3.2 сделал видимый признак условным.

**Два запрета — часть контракта**, того же класса, что два запрета §4.1:

- **признак не делается флагом «смонтировано»** (`useState` + запись в эффекте): это ровно
  `react-hooks/set-state-in-effect`, за который проект уже платил PR #41 (context.md вопрос 20),
  плюс второй рендер каждого перечня;
- **разметка не расходится между сервером и клиентом** — ни узлом, ни атрибутом, ни классом,
  поставленным условно от факта гидратации.

Оба действуют независимо от решения дизайна: они запрещают способ, а не требуют признака.

**Момент до гидратации — ответ на design §3.2 п. 4.** Дизайн назвал состояние: скрипты есть,
признак уже виден, обработчик ещё не подключён, — и отдал вопрос сюда.

**Средства, которое это состояние убирает, нет, и это следует из устройства, а не из бюджета.**
Отличить «скрипты доступны» от «обработчик подключён» может только то, что подключается вместе
с обработчиком, то есть сам JS: CSS факта гидратации не видит, а серверная разметка о нём знать
не может. Значит в этом окне одна из двух вещей неизбежно неверна — либо признак стоит раньше
обработчика (сегодня), либо имя выглядит инертным, пока страница уже отрисована.

**Средство, меняющее знак состояния, существует, и оно дороже остатка.** Оно не в состоянии
React, а в императивной записи класса на узел после монтирования: ни расхождения при гидратации
(первый клиентский рендер совпадает с серверным, класс приходит после), ни второго рендера.
Цена, из-за которой оно не берётся:

- признак приезжает **позже разметки у каждого посетителя и на каждой загрузке** — то есть
  редкое состояние чинилось бы видимым изменением обычного, ровно тем обменом, который отвергнут
  в направлении правила выше;
- что видит посетитель в обычном состоянии — предмет дизайна, а не мой, и механизм не вправе
  менять это молча;
- признак становится зависимым от того, что эффект отработал, — а `@media (scripting: none)`
  не зависит ни от чего.

Отсюда третий запрет, того же класса, что два выше: **окно до гидратации не лечится ни
предзагрузочным скриптом, ни разметочным различием** — оба возвращают запрет о расхождении.

**Наблюдение, которое сузит окно, но контрактом не является:** React записывает дискретные
события, пришедшие в ещё не гидратированное поддерево, и воспроизводит их после гидратации, —
тогда клик в этом окне открывает панель с задержкой, а не «не делает ничего». Утверждать это из
чтения кода нельзя, как и клиентскую навигацию в §4.1: проверяется на preview. Ни на контракт,
ни на приёмку не влияет — состояние принято дизайном в обе стороны.

**Граница.** Ставить ли признак условным — решено дизайном (PRD §10, его §3.2). Механизм и все
три запрета — мои. Имя класса, место объявлений и запись медиа-запроса (Tailwind v4:
`@custom-variant` или обычное правило) — кодера. Проверка — A13. [A §13.1]

### 4.4 Доводка раскрытой панели в поле зрения (AC 30)

Требование — PRD v2.6 §9.3 AC 30, шесть пунктов, проверка человеческая; правило — design §3.7;
порога нет (`D17`, закрыт владельцем 2026-08-28). PRD §10 отдал мне и кодеру одно: где живёт
шаг «раскрыли → измерили → доскроллили» и чем он прокручивает.

| | |
|---|---|
| Цель | **узел панели** — тот, чей `id` стоит в `aria-controls`. Не имя и не пара «имя + панель» (design §3.7 п. 5) |
| Где живёт | в обработчике клика по имени, внутри `PoiList`, то есть в одном месте на оба вида (PRD AC 16, §7.3) |
| Момент | после **синхронного** коммита состояния (`flushSync`), в том же обработчике: до коммита панель `hidden` и геометрии не имеет. Не в эффекте — [A §14] |
| Чем | `panel.scrollIntoView({ block, inline: 'nearest', behavior })`. Своего расчёта смещения нет: `nearest` не двигает страницу, когда цель видна целиком (пункт a), и смещает ровно на нехватку, в обе стороны (пункт b) |
| `block` | `'nearest'`, **кроме** случая «панель выше видимой области» — там `'start'` |
| Почему ветка обязательна | у цели, которая выше окна и начинается **ниже** верхней кромки, `nearest` выравнивает нижние края: начало текста уходит за верх экрана — исход, который пункт c называет провалом |
| Чем ветка не является | порогом. Сравниваются два размера — высота панели и высота видимой области, — а не доля видимого. `D17` снял долю; ветка приходит из пункта c, а не из осторожности |
| Когда не вызывается | при закрытии: повторный клик по тому же имени, `Escape`, клик вне блока (пункт e). Вызов стоит в ветке «открыли», поэтому пункты e и f выполняются по построению — клик по второму имени одно действие, один вызов, по вновь открытой панели |
| Без JS | вызывать нечего: панель не раскрывается |

**Ловушка предков: `scrollIntoView` прокручивает все контейнеры-предки, а `.tour-card` им
является.** `overflow: hidden` создаёт скролл-контейнер — невидимый, полос у него нет, — и
сдвинутое в нём содержимое само не возвращается. Сегодня вызов до него не дотягивается, и это
выведено, а не предположено:

- **блочная ось.** `.tour-card` — `display: flex; flex-direction: column`, высота задаётся
  содержимым (`app/globals.css:145-154`) `[from code]`. Содержимое не может стать выше
  карточки: панель её раздвигает. Диапазон прокрутки нулевой, а на нулевом диапазоне не
  двигают ни `nearest`, ни `start`. Крупный шрифт браузера этого не меняет — высота карточки
  растёт вместе с содержимым, — то есть ловушка не открывается ровно там, где ветка `'start'`
  впервые срабатывает;
- **строчная ось.** Панель занимает ширину контента карточки, то есть при `scrollLeft = 0`
  видна целиком, и `inline: 'nearest'` не двигает. Единственный источник строчного
  переполнения внутри карточки — слово шире колонки (design §3.1) — переполняет не панель;
- **страница даты.** У списка нет ни одного предка с `overflow`
  `[from code, app/[locale]/tours/[tourEventId]/page.tsx, app/globals.css]`. Ловушки там нет вовсе.

**Условие, при котором это перестаёт быть верным, и средство** — названо, чтобы отказ не искали
в прокрутке: как только `.tour-card` получит заданную высоту (или любой предок панели —
ненулевой диапазон прокрутки), `overflow: hidden` на нём меняется на `overflow: clip`: обрезает
так же, скролл-контейнера не создаёт, `scrollIntoView` его пропускает. Сегодня не делаю —
это правка общего класса главной ради состояния, которого нет. Проверка A11 ловит ровно этот
отказ, потому что глазами он неотличим от «не прокрутилось ничего».

**Чем меряется ветка, чтобы она не соврала.** С PRD v2.6 пункт c создаётся **настройкой
посетителя**, а не длиной текста: крупнейший шаг шрифта браузера (тред `A1`). Под ним корневой
размер растёт, `rem`-отступы внутри панели растут, число строк растёт, а окно — нет. Условие
ветки от этого не портится, но только пока обе его стороны читаются **измерением в пикселях в
момент клика**. Поэтому в контракт входит и то, что кодер обязан взять:

| | |
|---|---|
| Высота панели | `panel.getBoundingClientRect().height` — рамочный бокс, дробная, после синхронного коммита. `rem`-отступы уже внутри неё, и это причина мерить, а не вычислять |
| Высота видимой области | `document.documentElement.clientHeight` — **та самая коробка, по которой выравнивает `scrollIntoView`** |
| Чего в условии не бывает | ни одной константы: ни «выше N px», ни величины в `rem` или `em`. Константа в `rem` растёт вместе с панелью и ветку опрокидывает, константа в `px` не растёт вместе с текстом |
| Почему не `visualViewport` | человек судит по видимой области, но API прокручивает **раскладочную**. Мерить визуальную значило бы уходить в `'start'` там, где `'nearest'` уложил бы панель целиком меньшим смещением, — ветка соврала бы в другую сторону и провалила бы пункт b вместо c |
| Граница | у панели ровно в высоту окна обе ветки дают одно и то же положение, поэтому допуска условию не нужно |

**Граница.** Моё — цель, момент, средство, ветка `block` и то, чем читаются обе её стороны,
«только на открытии» и условие по предкам. Кодера — `behavior` и `prefers-reduced-motion`
(design §3.7 п. 8), `scroll-margin`, если дизайн попросит отбивку от кромки, и как записан
синхронный коммит.

**Тред `A1` закрыт продактом 2026-08-28, механизм не тронут.** Ветка была написана потому, что
её требует критерий; ответ добавил к этому, что состояние **отгружаемое** — оно наступает при
обычной настройке доступности, а не только на гипотетически длинном описании. Проверка A11
дополнена этим случаем.

### 4.5 Имя как контрол: элемент и разметочный инвариант

Требование — design §3.1: имя переносится через строку как обычный текст
`[owner, 2026-08-28]`, и перенесённое имя остаётся **одним** контролом. Диагноз дизайна принят
как факт и не переразбирается: боксов два, и `<button>` движок кладёт атомарным
строчно-блочным боксом независимо от классов.

**`<button>` заменяется строчным элементом с ролью: `<span role="button" tabIndex={0}>`.**
Обёртка `inline-block` вокруг пары «имя + разделитель» снимается вместе с кнопкой; разделитель
остаётся соседним узлом и держится неразрывным пробелом — в строчном потоке это работает, у
атомарного бокса не работало.

Что при замене обязано держаться (проверяется A12):

| | |
|---|---|
| **Один контрол на имя** — наблюдаемое требование design v1.4 §3.1, и оно первое, потому что из него следует всё остальное | один элемент и один строчный бокс на имя, по всей цепочке. Ни `inline-block`, ни `inline-flex`, ни `display: contents`. Перенесённое имя не распадается на два: область нажатия — все его строки, доступное имя одно, признак и рамка фокуса идут по обеим |
| Роль и состояние | `role="button"`, `aria-expanded`, `aria-controls` на `id` панели — как у нынешней кнопки, один в один |
| Клавиатура | `tabIndex={0}`; срабатывание по `Enter` **и** по `Space`, причём `Space` гасит прокрутку страницы. Нативная кнопка давала это даром, роль не даёт — это и есть цена замены |
| Доступное имя | только имя места: разделитель стоит вне контрола и `aria-hidden` |
| Фокус | видимый, через `:focus-visible`. На перенесённом имени рамка рисуется по фрагментам строк, то есть продолжается на второй, — это и требовалось |
| Пунктир | `text-decoration` строчного элемента, поэтому продолжается на переносе по построению, а не отдельным правилом |
| Цель прокрутки | не меняется: §4.4 прокручивает к узлу панели, а не к контролу |

Связь с §4.3.2: признак вешается на этот же элемент, и без JS этот элемент остаётся
фокусируемым и объявляется кнопкой — тот самый остаток, который CSS не снимает.

**Граница.** Моё — элемент и таблица выше. Кодера — классы, запись обработчика клавиш,
оформление рамки фокуса, техника неразрывности. Расхождение с design §1 названо в §1. [A §13]

S1 и S1′ разделены только потому, что S1 уже лежит в рабочем дереве (untracked,

**Что лежит в репозитории и что нет.** Таблица связей — очередь релиза (PRD §5.1,
вариант (b) владельца): место связывается только когда написаны оба описания. В
рабочем дереве сегодня **один** POI — `Acap: [{ poi: 'capitol' }]`, и его описание
пока `'TBD'` `[from code]`. Набор из 30 POI §9 — **материал, а не выпускаемый
набор**: имена, ссылки на карту и связи скомпилированы вне проекта и заезжают в
данные по мере появления описаний. Отсюда: контентом не блокируются S1/S1′ и S2, а
S3–S5 и S7 упираются в описания — по одному месту, а не по программе целиком.

**S6 — особый случай:** сам код от контента не зависит, но его приёмка зависит. A9
проверяет, что описание есть в серверном HTML, а AC 28 — что в блоке стоит тот же
текст, что на странице каталога; пока единственное описание в данных равно `'TBD'`,
проверять нечего (PRD §8). Значит S6 пишется когда угодно, а засчитывается не раньше
первого написанного описания.

**Проверка перед мержем `dev` → `main`:** `grep -c "'TBD'" data/poi.ru.ts
data/poi.en.ts` должен дать 0.

Это **страховка от промаха, а не ворота на каталог**. Под очередью релиза `'TBD'` в
данных не появляется вовсе, поэтому проверка истинна на каждом релизе, а не только на
последнем; она ловит единственный случай, который очередь пропустить может, — место,
связанное раньше своего текста. Билд его не поймает: строка непустая, AC 3 формально
выполнен. Воротами на полноту каталога она не является и являться не может — полноты
нет (PRD §5.1, AC 2 отозван).

## 8. Приёмка — что добавляется к AC PRD

Ни один пункт ниже не проверяет **состав и порядок элементов внутри записи** и форму
переходов: это требование чужого документа — design §2.2 и §3.1–§3.3, — и проверяется
по нему. Здесь проверяется то, что задал я: данные, инварианты, метаданные, механика
прибытия и порядок каталога, заданный PRD.

- **A1.** `curl` по `/ru/places/` и `/en/places/` на preview: `<link rel="canonical">`
  указывает на саму страницу со слэшем, три `hreflang` присутствуют. Проверяется на
  отрендеренном HTML, не в исходнике (context.md вопрос 17).
- **A2.** ✅ **Проверено 2026-08-13, оба случая.** POI без текста в EN →
  `Type error: Property 'innerSpaceCavern' is missing … in type 'Record<…, PoiText>'`;
  POI в текстах без программы → `'capitolX' does not exist in type 'Record<…>'`.
  Оба раза `npm run build` завершается кодом 1, после восстановления данных — кодом 0.
  **Проверять только билдом.** `npx tsc --noEmit` в этом репозитории обрывается на
  `tsconfig.json(25,5): error TS5101` (устаревший `baseUrl`) и не проверяет ни одного
  файла — молча возвращает «ошибок нет». Дефект существующий, к POI отношения не имеет,
  но как ворота `tsc` использовать нельзя.
- **A3.** Последовательность имён POI в программе — та же в RU и EN и та же в
  аккордеоне и на странице даты (PRD AC 7, AC 16). Проверяется сама
  последовательность, не форма перечня: форма — design §3.1. Следует из того, что
  таблица связей одна и не локализована, — но проверяется глазами на S3.
- **A4.** Свёрнутая мобильная карточка выглядит как сегодня **при заходе без якоря
  `<id>tour-card`** — открыть `/ru/` на мобильном и убедиться, что все карточки тизеры,
  включая ту, к которой ведёт ссылка из каталога. Прибытие по ссылке — отдельный
  случай, он в A5. Проверка AC 15 на отрендеренном HTML главной до починки issue #53
  верна только для первых трёх программ (PRD AC 15, абзац «How to check it until…») —
  остальное берётся со страницы даты.
- **A5.** Прибытие по ссылке (§4.1) — три вещи разом, по AC 25: прокрутка к карточке,
  разворот списка и **состояние карточки по прибытии: раскрыта, описание программы
  видно без дополнительного тапа**. Проверяется в обеих локалях и в двух раскладках:
  на десктопе (раскрытие даётся существующим кодом) и на мобильном, где оно и есть
  предмет проверки. Заодно проверяется, что кнопка «свернуть» на прибывшей карточке
  работает, а соседние карточки остались тизерами.
  Процедура для ветки «карточка не отрисована», не требующая правки кода: окно уже
  трёхколоночной раскладки (`< 1154px` = `350×3 + 32×2 + 40`, `ToursSection.tsx:19`)
  → главная рендерит три карточки, `Acap`, `Haust`, `Gcrt`
  `[from code, data/tours.ts]`. Значит проверять надо на программе с индексом ≥ 3;
  первая такая в очереди описаний — `Brmn` (индекс 4). До её появления в данных ветка
  не наблюдаема: единственная связанная программа `Acap` отрисована всегда. **Отсюда
  порядок: S2 проверяется полностью только вместе с S5**, до этого — «ссылка приводит
  к карточке, которая уже на экране, и та раскрыта».
  Смотреть **после гидратации**: до неё компактная раскладка ещё не определена
  (`useMediaQuery` отдаёт `false`, issue #53), и карточки развёрнуты по другой
  причине.
- **A6.** Алфавит. Сверка «RU и EN показывают один каталог» — сравнение множеств, не
  построчное: порядок между локалями расходится намеренно (PRD AC 26). Проверяется на
  S3, где записей больше одной.
- **A7.** Утверждение §2.6 срабатывает: временно опустошить `programPoi` вместе с
  файлами текстов → `npm run build` завершается кодом 1. Проверять билдом, не
  `npx tsc --noEmit` — причина в A2. **Не проверено, в отличие от A2.**
- **A8.** Прибытие на запись каталога (§4.2), два пути и оба обязательны: (1) переход по
  ссылке-иконке с главной — клиентская навигация, страница уже загружена; (2) открытие
  `/{locale}/places/#poi-<id>` как нового документа — вставить адрес в адресную строку.
  В обоих случаях запись должна оказаться в поле зрения без ручной прокрутки. Проверять
  на месте, которое **не первое** на странице (PRD AC 29), и в обеих локалях — якорь
  один, а порядок записей локалью различается (AC 26). Это же и есть проверка решения
  «`HashScrollHandler` сюда не монтируется»: промах на любом из двух путей означает, что
  решение неверно, а не что вёрстка съехала.
- **A9.** Серверная разметка описаний (§4.3) — `curl` по `/ru/` и по странице даты:
  текст описания места **присутствует** в отрендеренном HTML, при этом внутри самого
  перечня стоят только имена, а описания лежат в скрытых узлах блоков. Две половины
  проверяются разными способами и обе обязательны: наличие текста — из терминала,
  «список печатает имена» — глазами (PRD AC 15). Проверять с выключенным JS тоже:
  текст обязан читаться, блок при этом может не открываться — это принято. Как в этом
  состоянии выглядит **имя**, проверяет A13.
- **A10.** Область действия правила (§4.3) — **список, а не страница**, поэтому проверок
  две и вторая проверяет отсутствие связи, а не её наличие:
  1. **Внутри одного списка открыт максимум один блок.** Открыть блок у одного места,
     затем у другого в том же списке — первый обязан закрыться. Проверяется в аккордеоне
     и на странице даты, то есть в обоих родителях одного компонента.
  2. **Списки независимы.** На главной развернуть две карточки, открыть блок в каждой —
     **оба остаются открытыми**; это ожидаемое поведение, а не дефект
     `[owner, 2026-08-26]`. На месте, попавшем в два списка (`capitol` в `Acap` и
     `Auswe`), то же самое: открытие в одной карточке блок в другой не закрывает и не
     открывает. До появления `Auswe` в данных проверяется на двух разных местах в двух
     карточках.
- **A11.** Доводка прокручивает **страницу, а не карточку** (§4.4). Открыть панель у места в
  нижней части развёрнутой карточки на главной, так чтобы панель была обрезана снизу: страница
  смещается, панель встаёт впритык к нижней кромке (AC 30 b), **и содержимое самой карточки не
  сдвигается** — `scrollTop` и `scrollLeft` равны нулю **у той карточки, в которой шёл клик**:
  в консоли `$0.closest('.tour-card')` при выделенном имени, а не `document.querySelector('.tour-card')`.
  Адресация здесь несущая, и это правка v1.4 по треду `T14`: `querySelector` возвращает первую
  карточку документа, а нажатое имя почти никогда не в ней, — снимались бы нули с соседа,
  у которого прокрутки нет ни при каком исходе, и проверка не умела бы провалиться. Нули сами
  по себе ничего и не подтверждают: по выводу §4.4 диапазон прокрутки у `.tour-card` сегодня
  нулевой, — подтверждает то, что они сняты с правильного узла, иначе появление диапазона
  проверка проспит. Без этой второй половины отказ «прокрутилась карточка» неотличим от «не
  прокрутилось ничего»: обе выглядят одинаково. AC 30 целиком этим не заменяется — он
  человеческий и проверяется по своим шести пунктам.
  Вторым заходом — то же самое **при крупнейшем шаге шрифта браузера** (AC 30 c, тред `A1`):
  панель становится выше окна, страница обязана прийти верхом, и карточка снова не должна
  сдвинуться. Это единственный заход, где срабатывает ветка `'start'` (§4.4).
- **A12.** Имя как контрол в строчном потоке (§4.5) — на узкой раскладке и на самом длинном
  русском имени: имя переносится по словам; пунктир идёт по обеим строкам; разделитель строку
  не начинает; `Tab` доводит фокус до имени и рамка видна; `Enter` и `Space` открывают панель,
  причём `Space` страницу не прокручивает; инспектор доступности называет только имя места.
- **A13.** Условный признак (§4.3.2). С выключенными скриптами у имени нет ни пунктира, ни
  курсора-указателя; с включёнными — есть; и **в консоли нет предупреждений о гидратации**.
  Вторая половина обязательна: она и есть проверка запрета о расхождении разметки.
  Сравнения двух серверных ответов между собой здесь больше нет — правка v1.4 по треду `T17`:
  ответ сервера от того, исполняет ли клиент скрипты, не зависит и зависеть не может, поэтому
  байты совпадали бы и при нарушенном запрете. Запрет нарушается расхождением серверного HTML
  **с первым клиентским рендером**, а его ловят ровно предупреждения о гидратации. Кому нужно
  свидетельство глазами, сравнивает серверный ответ с DOM после гидратации — это другая
  проверка, и она необязательна. Вид в этом состоянии проверяет дизайн (v1.4 §3.2: имя не
  отличается от инертного имени каталога) — здесь проверяется механизм.

## 10. Открытые вопросы к владельцу

Пп. 1–6 не блокируют ни один срез и касаются содержания каталога, не модели.
Пп. 7–9 добавлены ревизией; блокирующих среди них нет — исходы названы у каждого.
Номера стабильны и не переиспользуются — та же конвенция, что у AC и рисков PRD:
закрытый пункт сохраняет номер и говорит, чем закрыт.

1. `Norwood building` — это Norwood Tower (7-я Западная)? Прочитано как она.
2. `TxDOT Headquarters` — историческое здание Dewitt C. Greer? Ссылка ведёт туда.
3. `Henry Hirshfield honeymoon cottage` — принято написание Hirshfeld.
4. «Масонский храм» в Джорджтауне — нужно точное название.
5. `Ann W. Richards Congress Avenue Bat Bridge` — принято официальное
   Ann W. Richards Congress Avenue Bridge, без «Bat».
6. `landOffice` — сегодня это Capitol Visitors Center, он же точка встречи `Haust`.
   Пересечения не делаем (§6 PRD: точка встречи и POI не связаны), но название на
   странице стоит выбрать одно. Дизайн вынес это же в тред D14; ответа нет, риск
   записан в PRD R16.
7. **Три видимые строки без источника** — подпись перечня программ в записи каталога,
   подпись группы дня и `description` страницы для поисковой выдачи (§6). PRD §7.4
   объявляет, что называет все строки, которые фича добавляет, но называет три из
   шести. Сегодня показываются значения, придуманные v1.0 этого документа, — то есть
   дефект, который §7.4 закрывал, закрыт наполовину. **Исход: меняет решение.** Слоты
   заданы, кодер заводит ключи, значения заменяются одной правкой `messages/*.json`.
   Отдельно стоит `description`: страница живёт поисковой выдачей (PRD §2), и это
   единственная из трёх строк, которую посетитель видит **до** захода на сайт.
   **Ведёт этот пункт по-прежнему мой документ, а не PRD** — в отличие от двух строк
   всплывающего блока (§6), которые PRD v2.4 завёл открытым пунктом O21 и ведёт сам.
   Три моих слота от этого не закрылись: в §7.4 PRD их по-прежнему нет.
8. ✅ **ЗАКРЫТ ответом владельца 2026-08-18 (O20), «да, раскрыть».** Было: по ссылке
   из каталога посетитель на мобильном попадает к свёрнутому тизеру, а AC 25 говорит
   «lands the visitor … at that program's description». Решено: карточка приезжает
   раскрытой на любой ширине; требование — PRD AC 25, механика — §4.1, цена
   (ослабленное ограничение на компактную ветку) — §4 и §8 A4.
9. **Русская страница читается как два алфавита.** Латиница в русской коллации идёт
   перед кириллицей, а у трети имён в наборе §9 русское имя латинское
   (`Old Bakery & Emporium`, `Millett Opera House`, `Norwood Tower`,
   `Austin History Center`, `North Cottage`, `Chateau Bellevue`,
   `Southwestern University`). Решение
   владельца это не отменяет — следствие названо, чтобы «алфавитный порядок» не
   оказался не тем, чего он ждал. **Исход: к сведению.**
